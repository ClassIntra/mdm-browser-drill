# 防御侧配对(Detection Pairing)与厂商修复建议

> 对应 `01-演习方案.html` §8。思路沿用 exploits 仓库「进攻模块必有防御侧目录」的纪律:
> 每一条「可能被放行的形态」,都给出本地检测信号与引擎修复动作。

## 一、形态 → 检测 → 修复 → 止损 对照

| 可放行形态(实测对象) | 本地/管理端检测信号 | 引擎修复建议(厂商) | 管理端止损 |
|---|---|---|---|
| URL 字符串匹配:userinfo / query / 任意位置含放行域名 | 出现 `@` 的导航与子资源请求即告警;命中「放行域名串 + 解析 host 为 IP」模式 | 判定点改为「解析后 host:port 精确匹配」;userinfo 拒绝或剥离后再判定 | 策略项新增「禁止含 userinfo 导航」;相关事件上报 |
| 子资源逐请求字符串判定 | 日志聚合:同源页面出现「域名串 + IP host」子资源突发 | 统一在解析后 host 上做判定,URL 先规范化(大小写/编码/端口) | 对含 @ 的资源请求降级拦截并记录 |
| 明文 WebSocket 放行 / 热点旁路 | 非白名单目标 TCP 建立的周期审计;137 网段流量识别 | WS 握手纳入同一规则;默认端口归一 | 课堂热点纳入策略覆盖或物理隔离 |
| 过滤器确定性 / 策略同步窗口 | 拉取时刻前后 1-2 分钟加强审计(本演习 A/B 定案) | 策略原子生效 + 生效版本时间戳上报 | 关键时段收窄窗口,生效前维持上一策略 |
| CIDR 条目存在但引擎不解析 | 定期「条目-引擎」一致性巡检 | 实现 CIDR 解析或移除误导性条目 | 管理端 UI 明示网段条目需引擎支持 |

## 二、本地(部署 owner)可持续检测

1. **入口 URL 审计**:对 40 网段受管设备的 http 明文流量,记录 URL 原文;凡含 `@`、含「放行域名串但 host 是内网 IP」的导航/请求,单独成表。
2. **UA/引擎登记**:按 X5 / 系统 WebView 分桶统计行为差异,防止引擎漂移导致误判。
3. **策略一致性巡检脚本**:比对「白名单清单(CIDR/域名/IP)」与「实测可达目标」,输出差异(文档 §10.1 已有先例)。

## 三、给厂商漏洞报告的证据链(建议附件)

1. URL 字符串匹配而非 host 解析(基线文档 §二.1/§10.1 + 本演习 N1-N7)。
2. userinfo 形式可过导航层,且浏览器规范导致 fetch 抛错/XHR 剥离/图片剥离 —— 说明该问题在纯客户端无通用利用(文档 §二.3)。
3. CIDR 条目(192.168.40.1/24)在策略中但引擎不解析(文档 §10.1)。
4. 过滤器确定性 A/B 结果(本演习 §7)与策略同步窗口证据。
5. 修复建议:解析后 host 精确匹配 + 拒绝 userinfo + 端口归一 + CIDR 引擎或条目下线。

> 本文件不构成对任何第三方系统的测试授权;仅适用自有环境。

# 讯飞学生机网址过滤实测：怎么拦的，怎么绕的

> 前期提要：本文部分内容仅为个人观点和玩梗。

讯飞学生机（智慧课堂学生平板）有一套内置的网址过滤。它管得比想象中宽：不光管你能不能上网，连访问内网都管。我们之前写过 captive（绕过 40 网段封锁访问超脑本地服务）和 noVNC（基于浏览器的超脑远控），那两篇的前提都是请求能正常发出去。这篇要讲的，是浏览器里更深一层的东西——它会在请求还没发出去之前就先拦一道。

先说现象。在 40 网段里直接访问超脑的地址，比如 `http://192.168.40.90:9001`，页面不会出现常见的"连接被拒绝"，而是显示"无效的响应"。这两个提示看着像一回事，其实来源完全不同："连接被拒绝"是网络层真的拒绝了；"无效的响应"是有人伪造了一个空响应回来——也就是说，这个拦截发生在浏览器内部，目标服务器那边根本收不到任何请求。

我们对这道过滤做了完整的黑盒测试，把它的判定规则摸清了。结论直接给：**它拦的不是"白名单以外的网站"，而是一张写死的黑名单，里面只有三个地址**。这张名单匹配方式是纯字符串比对，漏洞也很明显。下面先讲规则，再讲能怎么用。

---

## 一、过滤规则（结论先行）

浏览器发出的每一个请求，都会先经过一道判定。判定的依据是网址的"authority"部分——也就是 `http://` 后面、第一个 `/` 之前的那一段，形如 `用户名@主机:端口`。

规则只有几条：

1. **黑名单里只有三个 IP**：`192.168.40.1`（网关）、`192.168.40.90`（超脑）、`192.168.125.1`（课堂互动网关）。名单以外的地址一律放行——不管是内网其他机器、公网 IP，还是 172.16 段的上网认证服务器。
2. **匹配是纯字符串子串比对**，不是 IP 解析。比如 `192.168.40.100` 也会被拦，因为 `192.168.40.1` 是它开头的子串。名单条目是手工写的，`/24` 这类网段写法不会被解析，连网络地址本身都会被当成字面量拦下来。
3. **不分端口、不分协议通道**：三个地址的所有端口都拦；顶层导航、XHR、WebSocket 走同一套判定。
4. **不区分大小写**。

关键的一点是判定发生的位置：**过滤看到的是请求发出前的原始网址，而不是真正发出去的那个**。网页里的 `fetch`、图片、脚本在发出请求时会把网址里的"用户名"部分剥掉，但过滤看的是剥离之前的字符串。这给了绕过留了口子。

## 二、绕过方式（可直接使用）

### 方式 A：在地址前加一段任意字符

网址里 `@` 前面那一段（userinfo）本来就是给登录凭据预留的位置，现在的网站基本不用了。而这道过滤有个特点：**只要 `@` 前面有内容，它就只检查那一段，完全不看后面的主机名**。

所以访问超脑，把书签存成：

```
http://a@192.168.40.90:9001/
```

`@` 前面任意非空字符都行，实测单个字符 `a` 即可，请求 64ms 内到达。这条适用于浏览器直接打开、页面里的 XHR、WebSocket。代价是：`fetch` 会直接在构造时报错（浏览器不允许给带凭据的 URL 发 fetch，基于 fetch 的库会失效，axios 不受影响因为它走 XHR）；图片和脚本标签会被浏览器剥掉凭据再发，走不了这条；刷新后地址栏会被归一化，需要重新拼一次。

### 方式 B：用一个不含点分四段的域名

过滤对"主机名里嵌着 IP 形状字符串"的网址会按 IP 规则查，但如果主机名是普通域名、只是解析到内网地址，它直接放行。比如 nip.io 的横线写法：

```
http://192-168-40-90.nip.io:9001/
```

域名形态是完整解：fetch、绝对路径、图片、脚本、WebSocket 全部恢复原生行为，客户端不用任何改动。不止这一台靶机，任何不含点分四段、解析到内网地址的域名都一样。

### 方式 C：IPv6 映射写法（备用）

`http://[::ffff:192.168.40.90]:9001/` 也能通。浏览器会把这种写法规范化成十六进制形式，点分四段在规范化后消失，黑名单匹配不上。这个形态下页面里的相对路径请求也都能过，可以作为完整的一站式入口。缺点是地址栏形态比较怪，当备用方案。

### 已确认走不通的路

给服务器网卡加一个 `192.168.40.100` 的别名来访问——不行。因为黑名单是子串匹配，`40.100` 开头的 `40.1` 前缀会被连坐，一样拦。

## 三、验证过程概要

以上规则不是猜的，做了完整的黑盒验证：

- 两台受管设备：一台 X5 内核（Chrome/89），一台系统 WebView（Chrome/80 无 X5），结论完全一致，说明过滤不在浏览器内核里，而在 WebView 之下的系统层；
- 一共 62 个探针，覆盖导航、子资源、各种 URL 写法、端口、跳转方式；32 个关键探针的结果与规则零冲突；
- 每个探针都在自建靶机上留痕核对，页面显示只作参考——因为软拦是伪造响应，页面说的话不能信，只有请求是否真的到达才算数。

## 四、需要注意的几点

1. **探测和访问在目标侧都是零痕迹的**：软拦不产生任何真实网络请求，靶机日志里不会出现被拦的访问。这算个好消息，意味着这套方法本身不会在服务器上留下试探记录。
2. **WebSocket 会留痕迹**：WS 是唯一会把网址里的凭据原样带过去的通道，服务端能看到完整的来源。用 WS 之前想清楚。
3. **结论有快照时效**：规则基于当前策略和设备实测。如果厂商升级过滤逻辑，用三个探针就能快速回归验证（对应文末报告里的 DP5/29/32）。
4. 老规矩：不 root、不刷机、不装证书、不做中间人，能动的东西只有网址本身。

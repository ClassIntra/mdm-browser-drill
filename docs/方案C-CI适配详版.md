# 方案 C 详版 —— CI 在 40 网 WiFi 的 userinfo 形态临时适配

> 依据:演习定论 E1–E6(`02-首轮实测结论.html`)。性质:自有服务过渡方案,管理端白名单落地后撤除。
> 目标形态:入口 `http://spark.changyan.com@192.168.40.90:9001/`,页面内一切请求零改造即可过判定的部分靠"相对路径继承",不能继承的(XHR/WS)按本方案改造。

## 0. 原理一页纸

- 过滤器只看**每个请求"剥离凭据之前"的 authority 原始字符串**(E1),包含放行域名串(大小写不敏感)即放行(E2);
- 放行后凭据被剥离,**线上请求都是干净的**(E4)→ 服务器与 Cookie 一切照旧;
- 页面文档 URL 继承 userinfo 时,**一切相对路径资源/请求解析后自动带上 userinfo**(被 S6 证实)→ 这就是"脏文档"能带动全套子资源的机制;
- 两个硬约束:**fetch/EventSource 在 userinfo URL 上构造期必抛 TypeError**(E5)→ 只能用 XHR 和 WS;**干净绝对 URL 的子资源/请求 → 合成 404 软拦**(E3)→ 绝对路径必须消灭。

## 1. 入口层

1. 设备上做书签/桌面快捷方式:`http://spark.changyan.com@192.168.40.90:9001/`
2. **刷新陷阱(最重要)**:进入后地址栏被归一化为干净 URL(E4),此时刷新/回车 = 干净导航 = "无效的响应"。对策:
   - 前端 App 启动时检测 `location.href` 不含 `@` → 显示"重连入口"遮罩,一键执行
     `location.href = 'http://' + window.__CI_ENTRY__.dom + '@' + location.host + '/'`;
   - `history.replaceState/pushState` **写不回 userinfo**(浏览器安全限制),所以只能跳转重建,别试图改地址栏。
3. 域名串不写死:由 9001 服务端在首页 HTML 注入 `window.__CI_ENTRY__ = { dom: "spark.changyan.com" }`,换样本只改服务端。

## 2. 前端构建(vite)

- `base: './'`(全相对资源);路由建议 hash 模式(history 模式的刷新同样打干净 URL);
- 图标/字体/小图 dataURI 或相对路径;
- 排查第三方 SDK 硬编码绝对 URL(统计/CDN 字体等)——会被逐请求软拦,控制台报错,建议剔除;
- axios 可继续用(基于 XHR);项目里所有原生 `fetch(`/`new EventSource(` 必须清零(grep 检查)。

## 3. 请求层(XHR 化)

- 统一封装 `request()`,URL 一律写**相对路径**(`/api/...`)→ 解析后自动带 userinfo,XHR 自动剥凭据上线(S2/S6 双证实);
- **禁止** XHR 里写 `http://192.168.40.90:9001/...` 绝对地址(干净 authority → 软拦);
- 流式接口(ai-chat `/api/ai-chat/chat/stream`):fetch-ReadableStream 改为 **XHR onprogress 增量读**(`readyState===3` 时劈 `responseText`),或整体改走 WS;
- GET 动态接口加 `?r=`/时间戳防 XHR 内存缓存(演习同款坑);
- 上传下载 XHR `responseType` 不受限(blob/arraybuffer 均可)。

## 4. WS 层(聊天 10001)

- 客户端拼:`ws://' + window.__CI_ENTRY__.dom + '@' + location.hostname + ':10001`
- 明文 ws 已被 S7 + noVNC 先例证实可达;
- 注意 Origin:放行后 Origin 头是**干净形态** `http://192.168.40.90:9001`(E4 连带),服务端若校验 Origin 白名单,把干净形态加进去。

## 5. 服务端配合(9001 / 10001)

- 避免绝对 `Location:` 重定向(干净绝对地址的二次导航会被拦),用相对 Location;
- Cookie/会话照旧(线上请求本来就是干净形态);
- 日志保留 `:remote-addr`;服务器侧将只见干净请求,判定证据在设备侧,审计两面对照;
- 可选:加 `/entry-info` 端点输出当前入口配置,便于诊断。

## 6. 已知代价(如实告知)

| 项 | 影响 | 缓解 |
|---|---|---|
| 刷新/手输干净地址 | "无效的响应"拦截页 | 书签 + App 内重建入口按钮 |
| 分享链接 | 归一化干净链接,他人点了被拦 | "复制入口链接"按钮(前端拼 userinfo) |
| fetch 生态 | 依赖 fetch 的库/代码要重写 | axios 无碍;原生 fetch 逐个替换 |
| 依赖放行名单 | 域名串被移出名单/引擎修复即失效 | 定位为过渡;管理端白名单为终态 |
| 渲染体积 | 与普通版相同(大文档已被 E6 排除) | 无需内联巨型文档 |

## 7. 验收清单(适配完成后 10 分钟)

1. 书签进入 → 首页/静态/图标全加载;
2. 登录 + 普通接口(XHR)全 200;
3. ai-chat 流式回复正常(onprogress 或 WS);
4. 聊天 WS(10001)连接与收发正常;
5. 页内刷新 → 出拦截页 → 点"重连入口"恢复;
6. 服务器日志:所有请求源 IP=40.27、路径全干净(证明剥离上线正常)。

> 边界:仅用于自有部署的自有服务可达性;不做持久化、不装外部载荷;证据同步服务厂商漏洞报告与管理端工单。
